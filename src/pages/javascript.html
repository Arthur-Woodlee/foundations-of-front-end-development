JavaScript Module Patterns

Why Modules?

Modules are a way to bundle related data and functions into a single unit. Instead of scattering variables and logic across the global scope, modules give us a structured container where everything that belongs together lives together.

Why this matters

  • ✅ Encapsulation — keeps related state and behavior in one place
  • ✅ Clarity — readers immediately see which functions operate on which data
  • ✅ Maintainability — changes to one module don’t ripple unpredictably across the whole codebase
  • ✅ Reusability — modules can be imported, reused or composed in different contexts

Closures (Module Pattern)

Encapsulate private state using function scope. 

          
function closure() {
  let count = 0; // private
  return {
    increment() { count++; },
    getCount() { return count; }
  };
}
  • ✅ Private variables
  • ✅ Controlled public API
  • ❌ No inheritance or extensibility
  • ✅ supports composition for modular reuse

Object Literals

Simple, declarative structure for grouping related properties and methods. 

          
const logger = {
  level: 'info',
  log(message) {
    console.log('[${this.level}] ${message}');
  }
};
  • ✅ Easy to read and write
  • ❌ No private state
  • ⚠️ No built-in inheritance — but can be extended via Object.create()

Prototypal Inheritance

Use Object.create() or constructor functions to share behavior. 

          
const animal = {
  speak() { console.log('generic sound'); }
};

const dog = Object.create(animal);
dog.speak(); // "generic sound"
          
        
          
function Animal(name) {
  this.name = name;
}
Animal.prototype.speak = function () {
  console.log('${this.name} makes a sound');
};
  • ✅ Shared behavior via prototype chain
  • ✅ Memory-efficient
  • ❌ More verbose than classes

ES6 Classes

Syntactic sugar over prototypal inheritance. 

          
class User {
  constructor(name) {
    this.name = name;
  }
  greet() {
    console.log(`Hello, ${this.name}`);
  }
}
  • ✅ Clear syntax
  • ✅ Supports inheritance (extends)
  • ✅ Works well with modern tooling
  • ❌ No true private fields (until #private syntax)

Modules Summary

ES6 modules provide encapsulation by scoping variables and objects to the module context. When combined with class #private fields, they offer strong privacy — unless objects are explicitly exposed to the global scope.

Debugging Exposure

During development, you may want to inspect internal objects in DevTools. This can be done safely using conditional exposure: 

            
const ENV = 'development';

if (ENV === 'development') {
  window.secretInstance = secretInstance;
  console.log('🔍 Exposed for debugging');
}
  • ✅ Enables inspection during development
  • ✅ Keeps production scope clean
  • ⚠️ Avoid exposing sensitive logic or state

⚠️ Avoid attaching internal objects to window unless explicitly needed for debugging. In production, this breaks encapsulation and undermines privacy guarantees.

Hoisting in JavaScript

Hoisting is JavaScript’s way of handling variable and function declarations before code execution begins. Before the script is executed the engine first parses the code. Following are the steps.

  1. Creation phase (compile-time)
    The engine scans the entire scope. Function declarations are fully hoisted (made available before any code runs). Variable declarations are registered but not yet assigned values (they default to undefined).
  2. Execution phase (run-time)
    The engine executes code line by line. Variables receive their assigned values and functions can be invoked because their definitions were already hoisted.

This two-step process explains why you can call a function before it’s defined in the source code. Variables declared with var behave differently than those declared with let or const.

Best Practice

Declaring and initializing variables before you use them:

  • ✅ Avoids bugs from undefined or ReferenceError
  • ✅ Makes code more predictable and readable
  • ✅ Prevents confusion from the Temporal Dead Zone (let/const)
  • ✅ Aligns with strict mode and modern linters (e.g. ESLint)
          
let count = 0;
function increment() {
  count++;
}

When Hoisting Awareness Is Useful

While you shouldn’t depend on hoisting, understanding it helps you:

1. Avoid Bugs with var

            
console.log(x); // undefined, not ReferenceError
var x = 5;

Knowing this helps you refactor legacy code safely.

Understand Function Declarations vs Expressions

            
greet(); // ✅ works
function greet() { console.log("hi"); }

sayHi(); // ❌ TypeError: sayHi is not a function
var sayHi = function () { console.log("hi"); };
  • ✅ Function declarations are hoisted with their body
  • ❌ Function expressions (even with var) are hoisted as undefined

3. Enable Mutual Recursion

            
function isEven(n) {
  if (n === 0) return true;
  return isOdd(n - 1);
}
function isOdd(n) {
  if (n === 0) return false;
  return isEven(n - 1);
}

Both functions are hoisted, so they can call each other.

Module Initialization Order

            
const Module = (function () {
  init(); // ✅ works because function is hoisted

  function init() {
    console.log("Module initialized");
  }

  return { init };
})();

In IIFEs or module factories, hoisting awareness helps you structure declarations cleanly.

Understanding this in JavaScript

In JavaScript, this refers to the context object for the current execution and its value depends entirely on how a function is called, not where it's written. This chapter is a complete breakdown of every major scenario, with examples and gotchas.

Global Context

          
console.log(this); // In browser: Window object
  • ⚠️ In non-strict mode: this is the global object (window in browsers, global in Node.js)
  • ⚠️ In strict mode: this is undefined

Inside an Object Method

          
const user = {
  name: "Arthur",
  greet() {
    console.log(this.name); // "Arthur"
  }
};
user.greet();

this refers to the object the method is called on (user).

Standalone Function

          
function show() {
  console.log(this);
}
show(); // In browser: Window (non-strict), undefined (strict)

Not bound to any object → defaults to global or undefined in strict mode.

Arrow Functions

          
const obj = {
  name: "Arthur",
  greet: () => {
    console.log(this.name); // ❌ undefined
  }
};
obj.greet();
  • ⚠️ Arrow functions do not bind their own this
  • ⚠️ They inherit this from the surrounding lexical scope

Constructor Functions

          
function User(name) {
  this.name = name;
}
const u = new User("Arthur");
console.log(u.name); // "Arthur"

this refers to the newly created object.

Class Methods

          
class User {
  constructor(name) {
    this.name = name;
  }
  greet() {
    console.log(`Hi ${this.name}`);
  }
}
new User("Arthur").greet(); // "Hi Arthur"

Same behavior as constructor functions.

call, apply and bind

          
function greet() {
  console.log(this.name);
}
const person = { name: "Arthur" };

greet.call(person);  // "Arthur"
greet.apply(person); // "Arthur"
const bound = greet.bind(person);
bound();             // "Arthur"

These methods explicitly set this.

Event Handlers

          
document.querySelector("button").addEventListener("click", function () {
  console.log(this); // The button element
});
  • ⚠️ In regular functions, this refers to the element the event is bound to
  • ⚠️ In arrow functions, this is inherited from the outer scope

setTimeout and setInterval

          
const obj = {
  name: "Arthur",
  greet() {
    setTimeout(function () {
      console.log(this.name); // ❌ undefined or undefined
    }, 1000);
  }
};
obj.greet();
  • ⚠️ Regular functions lose this context
  • ⚠️ Use arrow functions or bind to fix:
          
setTimeout(() => {
  console.log(this.name); // ✅ "Arthur"
}, 1000);

DOM Inline Handlers

          
<button onclick="console.log(this)">Click me</button>
  • ⚠️ this refers to the DOM element (<button>)
  • 🧠 handler.call(element, event) — the browser eventually does this on the event
  • ❌ Arrow functions wouldn’t work in this context

Arrow Functions Inside Object Methods

Pitfall: Arrow functions don’t bind this.

          
const obj = {
  name: 'Arthur',
  greet: () => {
    console.log(`Hello, ${this.name}`);
  }
};

obj.greet(); // ❌ undefined — `this` is not bound to `obj`

Fix: Use a function expression.

          
const obj = {
  name: 'Arthur',
  greet: function() {
    console.log(`Hello, ${this.name}`);
  }
};

obj.greet(); // ✅ Hello, Arthur

Event Listeners

Arrow Function: this is inherited (not the element).

          
document.querySelector('#btn').addEventListener('click', () => {
  console.log(this); // ❌ `this` is not the button — it's inherited from outer scope
});

Function Expression: this is the element.

          
document.querySelector('#btn').addEventListener('click', function() {
  console.log(this); // ✅ `this` is the button element
});

Class Constructors

Arrow Function: this is inherited — useful for callbacks.

          
class Timer {
  constructor() {
    this.seconds = 0;
    setInterval(() => {
      this.seconds++;
      console.log(this.seconds); // ✅ Works — arrow inherits `this` from constructor
    }, 1000);
  }
}

Function Expression: this breaks unless bound.

          
class Timer {
  constructor() {
    this.seconds = 0;
    setInterval(function() {
      this.seconds++; // ❌ TypeError — `this` is not bound
    }, 1000);
  }
}

Fix: Use .bind(this).

          
setInterval(function() {
  this.seconds++;
}.bind(this), 1000);

fetch + then with Function Expression

          
const obj = {
  name: 'Arthur',
  fetchData: function() {
    fetch('/api/data')
      .then(function(response) {
        console.log(this.name); // ❌ undefined — `this` is not bound to obj
      });
  }
};

obj.fetchData();
  • ✅ function(response) creates a new this context
  • ❌ Not bound to obj unless you use .bind(this) or a closure
          
const obj = {
  name: 'Arthur',
  fetchData: function() {
    fetch('/api/data')
      .then(response => {
        console.log(this.name); // ✅ Arthur — arrow inherits this from fetchData
      });
  }
};

Promise.then in Class Method

          
class User {
  constructor(name) {
    this.name = name;
  }

  loadProfile() {
    Promise.resolve('done')
      .then(function() {
        console.log(this.name); // ❌ undefined
      });
  }
}

new User('Arthur').loadProfile();
            
        
          
.then(() => {
  console.log(this.name); // ✅ Arthur
});

setTimeout with Function Expression

          
const obj = {
  name: 'Arthur',
  greet: function() {
    setTimeout(function() {
      console.log(`Hello, ${this.name}`); // ❌ undefined
    }, 100);
  }
};
            
        
          
setTimeout(() => {
  console.log(`Hello, ${this.name}`); // ✅ Hello, Arthur
}, 100);

Event Delegation with Function Expression

          
document.querySelector('#parent').addEventListener('click', function(e) {
  if (e.target.matches('.child')) {
    console.log(this); // ✅ this is #parent
    console.log(e.target); // ✅ clicked .child element
  }
});
  • 🧠 this is bound to the element that the listener was attached to (#parent)
  • ✅ Ideal for delegation: you inspect e.target and act conditionally

Event Delegation with Arrow Function

          
document.querySelector('#parent').addEventListener('click', (e) => {
  if (e.target.matches('.child')) {
    console.log(this); // ❌ inherited — likely window or undefined
    console.log(e.target); // ✅ still works
  }
});
  • ❌ Arrow functions do not bind this
  • ⚠️ this is inherited from the enclosing scope — not the DOM element

DOM Callback with Function Expression

          
const button = document.querySelector('#btn');

button.addEventListener('click', function() {
  this.style.backgroundColor = 'red'; // ✅ this is the button
});

Works as expected.

DOM Callback with Arrow Function

          
button.addEventListener('click', () => {
  this.style.backgroundColor = 'red'; // ❌ TypeError — this is not the button
});

Arrow functions break this binding in DOM callbacks.

Arrow Functions vs Function Declarations and Expressions

In JavaScript, this behaves differently depending on whether you use an arrow function, a function declaration, or a function expression. The key difference is whether this is determined at call time or declaration time, and whether it can be rebound.

Function Declarations

          
function show() {
  console.log(this);
}
show(); // In browser: Window (non-strict), undefined (strict)
  • this is set by the caller (global object, or object before the dot)
  • Can be rebound using call, apply, or bind

Function Expressions

          
const obj = {
  name: "Arthur",
  greet: function() {
    console.log(this.name);
  }
};
obj.greet(); // ✅ "Arthur"
  • Behaves the same as declarations: this depends on the caller
  • Can be rebound explicitly

Arrow Functions

          
const obj = {
  name: "Arthur",
  greet: () => {
    console.log(this.name);
  }
};
obj.greet(); // ❌ undefined
  • Arrow functions do not bind their own this
  • this is inherited from the enclosing lexical scope
  • Cannot be rebound — call, apply, and bind have no effect

Summary: Regular functions determine this at call time and can be rebound. Arrow functions capture this at declaration time and cannot be rebound.

Asynchronous JavaScript: Promises and Async/Await

Promises

A Promise is a JavaScript object that represents the eventual result of an asynchronous operation. Think of it like a contract: “I promise to give you a result later either success or failure.”

Creating and Using Promises

          
const myPromise = new Promise((resolve, reject) => {
  if (/* success */) {
    resolve('Success!');
  } else {
    reject('Failure!');
  }
});

myPromise
  .then(result => console.log('Resolved with:', result))
  .catch(error => console.error('Rejected with:', error));
  • resolve() → moves to fulfilled
  • reject() → moves to rejected
  • .then() handles success
  • .catch() handles failure

Real Example: Simulating a Delay

          
function wait(ms) {
  return new Promise(resolve => {
    setTimeout(() => resolve(`Waited ${ms}ms`), ms);
  });
}

wait(1000).then(msg => console.log(msg)); // "Waited 1000ms"

Async/Await

Async/await makes asynchronous code look synchronous.

          
async function run() {
  const result = await wait(1000000);
  console.log(result);
}
run();
console.log("Yippee");
  • await pauses only inside the async function
  • Does not block the main thread
  • "Yippee" logs before the Promise resolves

Quirks with Await

          
// Sequential loop (works)
for (const ms of [1000, 2000, 3000]) {
  const result = await wait(ms);
  console.log(result);
}

// forEach (doesn't wait)
[1000, 2000, 3000].forEach(async ms => {
  const result = await wait(ms);
  console.log(result);
});

Error Handling with Await

          
async function run() {
  try {
    const result = await riskyPromise();
    console.log(result);
  } catch (err) {
    console.error('Caught error:', err);
  }
}

Always wrap await in try/catch if the Promise might reject.

Multiple Promises in Parallel

          
const results = await Promise.all([wait(1000), wait(2000), wait(3000)]);
console.log(results);

const settled = await Promise.allSettled([wait(1000), riskyPromise(), wait(3000)]);
console.log(settled);

Retrying Failed Promises

          
async function retryAsync(fn, retries = 3, delay = 1000) {
  for (let i = 0; i <= retries; i++) {
    try {
      return await fn();
    } catch (err) {
      if (i === retries) throw err;
      await new Promise(res => setTimeout(res, delay));
    }
  }
}
  • Exponential backoff
  • Jitter (random delay)
  • Retry only on specific errors

Function Declarations vs Function Expressions

Function Declarations

          
function doSomething() {
  // logic
}
  • Hoisted — available before it’s defined
  • Best for top-level utilities or module helpers
  • Clear stack traces with named functions
  • Classic procedural or library-style code

Example

          
// Works even though it's called before it's defined
sayHi();

function sayHi() {
  console.log("Hi!");
}

Function Expressions

          
const doSomething = function() {
  // logic
};
  • Control scope tightly (block or closure)
  • Assign functions to variables, properties, or arguments
  • Pass or return functions dynamically
  • Use in callbacks, IIFEs, higher-order functions
  • Name internally for recursion or debugging

Example: Scoped Logic

          
if (condition) {
  const handle = function() {
    console.log("Scoped handler");
  };
  handle();
}
// handle is not available here

Real-World Patterns

  • React/Vue: expressions for event handlers and hooks
  • Node modules: declarations for exported utilities
  • Closures: expressions to encapsulate logic
  • Dynamic behavior: expressions to return functions

Switching from Declarations to Expressions

Switching improves modularity, testability, and workflow clarity.

Encapsulated Utility in Modules

          
export const formatDate = function(date) {
  return new Intl.DateTimeFormat('en-AU').format(date);
};
  • Scoped to the export
  • Easy to mock or override in tests
  • Avoids hoisting surprises

Injectable Logic for Testing

          
const fetchData = function(apiClient) {
  return apiClient.get('/data');
};
  • Inject mocks for apiClient
  • Keeps function pure and testable
  • Supports dependency injection setups

Dynamic Composition

          
const handlers = {
  onClick: function() {
    console.log('Clicked!');
  },
  onHover: function() {
    console.log('Hovered!');
  }
};
  • Object-based composition
  • Useful in React props, Vue methods, event maps
  • Scoped and portable functions

Higher-Order Functions

          
const withLogging = function(fn) {
  return function(...args) {
    console.log('Calling:', fn.name);
    return fn(...args);
  };
};
  • Function wrapping and decoration
  • Modular and composable logic
  • Easy to test wrapped behavior

Function Declarations: Utilities & Helpers

Top-Level Utility

          
function formatDate(date) {
  return new Intl.DateTimeFormat('en-AU').format(date);
}
  • Declared at top of module
  • Hoisted and available throughout
  • Often exported for reuse

Module-Level Helper

                    
function normalizeUser(user) {
  return {
    ...user,
    name: user.name.trim(),
    email: user.email.toLowerCase()
  };
}
  • Supports internal module logic
  • Keeps workflows clean and modular
  • Not necessarily exported

Function Expressions: Higher-Order Functions

          
const withLogging = function(fn) {
  return function(...args) {
    console.log(`Calling ${fn.name}`);
    return fn(...args);
  };
};

function greet(name) {
  return `Hello, ${name}`;
}

const loggedGreet = withLogging(greet);
loggedGreet('Arthur'); // Logs + returns greeting
  • Assign functions to variables
  • Compose or inject behavior
  • Scoped and modular logic

Compositional Flexibility

What Do We Mean by “Composition”?

Function composition means building behavior by combining functions, often dynamically.

Flexibility here means:

  • Assigning functions inline
  • Passing them as arguments
  • Returning them from other functions
  • Wrapping or modifying them on the fly

Function Expression: Fully Composable

          
const double = x => x * 2;
const square = x => x * x;

const compose = (f, g) => x => f(g(x));

const doubleThenSquare = compose(square, double);
console.log(doubleThenSquare(3)); // 36
  • You can assign, pass and return functions inline
  • Works with anonymous or arrow functions
  • Ideal for dynamic pipelines, middleware or higher-order functions

Function Declaration: Less Composable Inline

          
function double(x) {
  return x * 2;
}

function square(x) {
  return x * x;
}

// Can't declare a composed function inline with `function`
const doubleThenSquare = function(x) {
  return square(double(x));
};
  • Must be declared ahead of time
  • Can’t be returned or passed inline without wrapping
  • Not ideal for dynamic composition

Real-World Example: Middleware Chain

With Expressions

          
const withLogging = fn => (...args) => {
  console.log(`Calling ${fn.name}`);
  return fn(...args);
};

const withValidation = fn => (...args) => {
  if (!args[0]) throw new Error('Missing input');
  return fn(...args);
};

const handler = x => `Processed ${x}`;
const enhanced = withLogging(withValidation(handler));

With Declarations

          
function handler(x) {
  return `Processed ${x}`;
}

// Can't compose inline without expressions

Patterns

debounce(fn, delay) — Rate-limiting noisy calls

Use Case: Prevent a function from firing too frequently (e.g., on input or scroll events). 

          
function debounce(fn, delay) {
  let timer;
  return function(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}
  • Encapsulates timing logic
  • Reusable across UI components
  • Keeps event handlers clean

memoize(fn) — Cache-heavy computations

Use Case: Avoid recomputation for expensive pure functions (e.g., Fibonacci, factorial, API calls). 

          
function memoize(fn) {
  const cache = {};
  return function(...args) {
    const key = JSON.stringify(args);
    if (cache[key]) return cache[key];
    const result = fn(...args);
    cache[key] = result;
    return result;
  };
}
  • Abstracts caching logic
  • Improves performance
  • Easy to wrap any pure function

compose(f, g) — Function chaining

Use Case: Combine multiple functions into a single pipeline (e.g., data transformation). 

          
function compose(f, g) {
  return function(x) {
    return f(g(x));
  };
}
  • Encourages declarative pipelines
  • Reduces nesting
  • Improves readability and testability

withLogging(fn) — Behavior injection

Use Case: Wrap any function with logging, timing, or error handling. 

          
function withLogging(fn) {
  return function(...args) {
    console.log(`Calling ${fn.name} with`, args);
    return fn(...args);
  };
}
  • Non-invasive instrumentation
  • Reusable across domains
  • Improves debugging and onboarding

throttle(fn, interval) — Limit execution rate

Use Case: Prevent a function from running more than once every interval ms (e.g., scroll, resize). 

          
function throttle(fn, interval) {
  let lastCall = 0;
  return function(...args) {
    const now = Date.now();
    if (now - lastCall >= interval) {
      lastCall = now;
      fn(...args);
    }
  };
}
  • Encapsulates timing logic
  • Reusable across UI and stat polling
  • Keeps event handlers lean

retry(fn, attempts) — Resilient execution

Use Case: Retry a function (often async) up to attempts times if it fails. 

          
function retry(fn, attempts = 3) {
  return async function(...args) {
    for (let i = 0; i < attempts; i++) {
      try {
        return await fn(...args);
      } catch (err) {
        if (i === attempts - 1) throw err;
      }
    }
  };
}
  • Wraps flaky APIs or async logic
  • Improves resilience
  • Easy to plug into fetch chains or service calls

applyMiddleware(...middlewares) — Composable logic layers

Use Case: Chain multiple functions to wrap a core handler (e.g., logging, auth, validation). 

          
function applyMiddleware(...middlewares) {
  return function(handler) {
    return middlewares.reduceRight((acc, mw) => mw(acc), handler);
  };
}

// Example Usage
const withLogging = fn => (...args) => {
  console.log('Calling with', args);
  return fn(...args);
};

const withValidation = fn => (...args) => {
  if (!args[0]) throw new Error('Missing input');
  return fn(...args);
};

const handler = x => `Processed ${x}`;
const enhanced = applyMiddleware(withLogging, withValidation)(handler);
  • Clean separation of concerns
  • Declarative logic stacking
  • Ideal for request pipelines, CLI tools, or stat processors

Var, Let and Const in Closures

Closure Pattern: Capturing and Mutating x

      
function createCounter() {
  let x = 0; // captured by closure

  return function increment() {
    x++;
    console.log(`x is now: ${x}`);
    return x;
  };
}

const counter = createCounter();
counter(); // x is now: 1
counter(); // x is now: 2
  • x is lexically scoped inside createCounter
  • increment forms a closure over x
  • Each call to counter() mutates the same x

let — Block-scoped, mutable

      
function makeLetCounter() {
  let x = 0;
  return () => ++x;
}
  • ✅ Works as expected
  • ✅ Mutable
  • ✅ Scoped to the function block

const — Block-scoped, not reassignable

      
function makeConstCounter() {
  const state = { x: 0 };
  return () => ++state.x;
}
  • ✅ Works if x is a property of an object
  • ❌ Cannot reassign state itself
  • ✅ Can mutate internal state

var — Function-scoped, hoisted

      
function makeVarCounter() {
  var x = 0;
  return () => ++x;
}
  • ✅ Works, but function-scoped not block-scoped
  • ⚠️ Hoisted to top of function
  • ⚠️ Can lead to bugs in loops or conditionals

Bonus: Pitfall with var in Loops

      
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// Logs: 3, 3, 3

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// Logs: 0, 1, 2
  • var shares the same i across iterations
  • let creates a new i per iteration
  • Closures capture the correct value with let

Why var Can Be Problematic in Closures

Function-scoped, not block-scoped

      
function demo() {
  if (true) {
    var x = 5;
  }
  console.log(x); // ✅ 5 — leaked outside block
}
  • var ignores block boundaries
  • Can lead to unexpected access or mutation

Hoisting Confusion

      
function demo() {
  console.log(x); // ❌ undefined, not ReferenceError
  var x = 10;
}
  • var is hoisted to the top of its function
  • Creates temporal confusion in closures

Loop Closure Trap

      
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// Logs: 3, 3, 3
  • All closures share the same i (value after loop ends)
  • ❌ Breaks expected behavior

Safer with let

      
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// Logs: 0, 1, 2
  • let creates a new i per iteration
  • Closures capture the correct value

Summary: Use var only when…

Scenario Use var?
Inside closures ❌ Avoid
In loops with async logic ❌ Avoid
Top-level legacy code ⚠️ Maybe
Modern modular JS ✅ Prefer let or const
